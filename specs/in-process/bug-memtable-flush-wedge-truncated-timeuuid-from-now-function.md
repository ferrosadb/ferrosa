# Memtable flush wedges forever when server-side `now()` writes an 8-byte value into a `timeuuid` clustering column

## Summary

A row in `agent_memory.tool_usage_log` was accepted at write time but cannot
be flushed to SSTable. Every periodic flush attempt (and the
pre-schema-persist flush) fails with the same error against the same row.
The memtable therefore grows unbounded across restarts (commit log replay
re-materialises the bad row) and the node OOMs. Once one node OOMs the
operator typically kills the rest of the cluster, taking ferrosa-memory
fully offline.

This is **P0 — full cluster outage with potential data loss** if not
recovered carefully.

## Observed error

`ferrosa-memory_node3_1` (every 30s, for the entire life of the node):

```
WARN ferrosa: periodic flush failed
  e=invalid data: ferrosa-sstable/writer:
    partition key="\0\u{10}<16-byte uuid>\0\n2026-04-28\0"
    row_idx=0:
    clustering column 0 (org.apache.cassandra.db.marshal.TimeUUIDType)
    expects 16 raw bytes but row provided 8
```

Earlier (once per restart):

```
WARN ferrosa: pre-schema-persist flush failed, skipping schema persist
  e=invalid data: ferrosa-sstable/writer: ... <same row>
```

The partition-key bytes decode as a CQL composite of `(uuid, text)` —
length-prefix `0x0010` then 16 raw UUID bytes, length-prefix `0x000a`
then ASCII `"2026-04-28"`. That uniquely matches `tool_usage_log`:

```cql
CREATE TABLE IF NOT EXISTS tool_usage_log (
    tenant_id uuid,
    day text,
    call_id timeuuid,
    ...
    PRIMARY KEY ((tenant_id, day), call_id)
) WITH CLUSTERING ORDER BY (call_id DESC);
```

(`entity_store` does not match — its clustering col is `uuid`, not
`timeuuid`, and its partition key is `(uuid, uuid)`.)

## Repro shape

The MCP server (`ferrosa-memory-core/src/cql_storage.rs:594`) prepares
this statement:

```cql
INSERT INTO {ks}.tool_usage_log
  (tenant_id, day, call_id, tool_name, repo,
   input_bytes, output_bytes, estimated_tokens, latency_ms, error)
VALUES (?, ?, now(), ?, ?, ?, ?, ?, ?, ?)
```

It is bound and executed on every tool dispatch, i.e. at high
sustained rate. The clustering value is computed **server-side** by
ferrosa's `now()` function. Some fraction of those `now()` invocations
produce an 8-byte payload in the memtable row instead of a 16-byte
TimeUUID. The router accepts the write, the commit log records it, and
the next periodic flush (and every subsequent one) blows up on this
row, blocking every other row in that memtable from reaching disk.

## Why this is a Ferrosa bug

- The client never binds `call_id` directly — it is generated by
  ferrosa's own server-side `now()` builtin. An 8-byte TimeUUID is
  malformed by the CQL spec (TimeUUID is exactly 16 raw bytes).
- The router accepts the row at write time even though the value is
  invalid for a TimeUUID-typed clustering column.
- The error only surfaces at flush time, *after* the row is durable
  in the commit log — so every restart reproduces the wedge and there
  is no clean way to drop the bad row without dropping the whole
  table (which would lose all historical tool usage).
- This violates the project's **Fail Loud, Never Fake** principle:
  the writer pretends the operation succeeded, then a background task
  silently degrades on every tick.

## Suspected root cause

`now()` in ferrosa's CQL layer is most likely returning a
`Long` / `BigInt` (the 8-byte millisecond timestamp portion of a
TimeUUID) somewhere along the path between the function builtin
and the memtable cell value, instead of a fully-constructed 16-byte
TimeUUID. Two plausible spots:

1. **Builtin function dispatch** — `now()` resolves to a function that
   returns an `i64` timestamp and gets bound to a TimeUUID slot
   without expansion to the 16-byte form (4-byte time_low, 2-byte
   time_mid, 2-byte time_hi_and_version, 2-byte clock_seq, 6-byte
   node).
2. **Prepared-statement coercion** — the prepared statement's bind
   metadata records the `?` for `call_id` (or the `now()` return
   slot) as a generic numeric/`Long` rather than `TimeUUID`,
   so the value is encoded as 8 bytes when the row is built for the
   memtable.

A targeted fix probably lives in the CQL function evaluation path
(`ferrosa-cql/src/.../functions.rs` or equivalent) and/or the
prepared-statement bind-type inference for column-typed expressions.

## Expected behaviour

- `now()` used in a `timeuuid` column slot must always materialise to
  a valid 16-byte v1 TimeUUID before the row enters the memtable.
- If a row's clustering bytes do not match the declared column type,
  the **write** must fail with `Invalid` at the router (fail-loud) so
  the client sees the error and can correct it. The flush path must
  not be where this is first detected.
- A flush failure on a single row must never wedge the entire memtable
  — see the "Salvage" requirement below.

## Required fix (3 layers — all required)

### Layer 1 — prevent further bad writes (root cause)

Fix `now()` (and any other server-side TimeUUID-producing function)
so its result is always a 16-byte TimeUUID when targeted at a
`timeuuid` column.

Add a router-side validator: before appending a row to the memtable,
check that every cell's encoded length matches its column type's
fixed length (TimeUUID=16, UUID=16, Int=4, BigInt=8, Float=4,
Double=8, Boolean=1, Inet=4 or 16, Timestamp=8). Reject the write
with `Invalid` if mismatched. This is the fail-loud guard.

### Layer 2 — recover the wedged cluster *without data loss*

The bad rows are durable in the commit log. A naïve restart re-wedges
the cluster. The fix must allow the cluster to come back up with
**all good data preserved** and the bad rows quarantined for
forensic recovery, not deleted.

Implement a **quarantine-on-flush** path in
`ferrosa-sstable/src/writer.rs` (or wherever periodic flush is
driven):

- When a row fails the per-cell length validation during flush,
  serialise the offending `(partition_key, clustering_key, full_row_bytes,
  declared_column_types, error_msg)` as a JSON line into a sibling
  file `quarantine/<keyspace>.<table>.<timestamp>.jsonl` under the
  data dir.
- Continue flushing the rest of the memtable to the SSTable.
- Bump a metric `FERROSA_FLUSH_QUARANTINED_ROWS_TOTAL{keyspace,table}`
  and emit one ERROR-level log per quarantined partition (not per
  row — be log-budget-aware on a wedged table).
- Do **not** delete the bad rows from the commit log; the quarantine
  file is the durable record of what was salvaged.

This satisfies the "no data loss" requirement: every byte the
client wrote is recoverable from either the SSTable (good rows) or
the quarantine file (bad rows). An operator can then inspect the
quarantine, derive the intended TimeUUID (the 8 bytes are very
likely the millisecond timestamp portion — reconstructible into a
v1 TimeUUID by adding clock_seq + node), and replay the salvaged
rows once the bug is fixed.

### Layer 3 — replay-time tolerance

`engine.rs` commit log replay must use the same per-cell length
validator and route invalid rows directly to the quarantine file
(skipping the memtable entirely on replay). Without this, a node
restart on an already-wedged cluster will replay the bad row into
a fresh memtable and re-wedge before Layer 2 can ever run.

## Recovery runbook (post-fix, for the operator)

1. Build the patched ferrosa image with all three layers above.
2. Stop the MCP server (`ferrosa-memory_ferrosa-memory-mcp_1`) so it
   stops sending `tool_usage_log` writes.
3. Start node1 only. Watch logs for
   `FERROSA_FLUSH_QUARANTINED_ROWS_TOTAL` increments and the
   quarantine file appearing under the data dir. Confirm the node
   reaches healthy.
4. Start node2 and node3.
5. Restart the MCP server. New `tool_usage_log` writes will be
   well-formed (Layer 1) and flush cleanly.
6. Hand the quarantine file to the on-call engineer for offline
   reconstruction of the salvaged rows.

**Do not** drop `tool_usage_log` and **do not** delete commit log
segments without first dumping the segments to a backup directory.

## Surface area / blast radius

Any table with a `timeuuid` clustering or partition column that is
populated via server-side `now()` is vulnerable. In ferrosa-memory
the candidate tables (from `ddl/`) are:

- `tool_usage_log` (confirmed wedged)
- `temporal_events.event_id`
- `trajectory_folds.fold_id`
- `feedback_outcomes.query_id`
- `entity_store.source_fold_id` (regular column, not clustering, but
  still TimeUUID-typed)

Check writers in `crates/ferrosa-memory-core/src/cql_storage.rs`
for any `now()` usage targeting a TimeUUID column and audit them
once Layer 1 lands.

## Test plan

- Unit test in `ferrosa-cql`: `INSERT ... VALUES (now())` into a
  `timeuuid` column; assert the bound value is exactly 16 bytes.
- Integration test in `ferrosa-cluster`: write 1000 rows via
  `INSERT ... now()` into a TimeUUID-clustered table; trigger a
  flush; assert SSTable contains exactly 1000 rows and quarantine
  file is empty.
- Regression test for the wedge: hand-craft a memtable with one
  bad-length cell + 99 good cells; trigger flush; assert SSTable
  contains 99 rows and quarantine contains 1, no panic, no retry
  loop.
- Replay test: write a bad row into the commit log directly,
  restart the node, assert the bad row is quarantined on replay
  and the node reaches healthy.
