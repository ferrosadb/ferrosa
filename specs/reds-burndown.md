# Lean reds burndown

## What "the reds" are

Two overlapping lists, both machine-checked, neither of which is a todo list:

| List | Count | What a row means |
|---|---|---|
| `red-ledger::REDS` | **107** | An unmet claim in a Lean area ledger. `tests/reds.rs` pins the count; CI runs `red_ledger.py --check`. |
| `Ferrosa/Broken.lean` | **56** | Built, shipping, and **wrong**: tells a customer something false today. |
| `Ferrosa/Unimplemented.lean` | 43 + 8 | No code path yet / not a defect (requirement, proof, measurement, inherited, closed). |

A red is data, never a test. Closing one means: write the test that pins the claim in the
crate that owns the code → flip the Lean item to `.met` → the generator drops the row.

## Method, and the finding that reorders everything

Every row below was verified **against the code**, not read off the ledger. Three parallel
audits re-read the sites at `v0.36.9`. Line numbers in the ledger have drifted and, worse:

> **Roughly half the rows audited so far describe code that has already been fixed since
> the ledger was written.** Main landed large workstreams between 2026-11-04 and 2026-11-16
> (streaming executor, `Arc` rows, bounded `TaskPool`, reserve-ahead commit-log markers,
> snapshot monotonicity, restore rollback) and the ledgers were never re-flipped.

That makes book-keeping the first deliverable, not a footnote: a burndown plan that trusts
this ledger would spend sprints re-fixing shipped code. It also means the red count is
currently **unknowable** — it is pinned at 107, but at least 8 of the 20 audited rows are
already false.

## Tier 1 — correctness

Ordered by *expected damage if left*, not by count or by effort. The governing question is:
what does a customer lose, and how many at once?

### C1 — A latched node can never be repaired in-process `[#33]` — availability, cluster-wide

**Defect.** `install_snapshot` calls `finish_pending_apply()` **first**
(`state_machine.rs:3061`), which returns the sticky failure before anything else
(`:655-661`). So the one message that would repair the node is refused before it is decoded.
`ConsensusHealth` exposes `fail`/`is_healthy`/`failure`/`failure_count` and **no reset**
(`consensus_health.rs:97-124`); `RecoveryAdmission` likewise has `quarantine()` and no
removal (`quarantine.rs:85-90`).

**Why this is first.** The latch is *terminal by construction* and the failure set is
deterministic in the **entry**, not the node: `flush_pending_system_writes` now returns `Err`
even for former `WarnReplay` sites (`:2704-2712`), `sync_projection` returns `Err` on any
`force_commit_log_sync` failure (`:2728`), and fatal `ApplyError` variants still fence
(`:158-165`). Every replica applying the same entry against the same class of local condition
latches at once, and openraft takes the core down (`let res = command_result.result?`,
`openraft/src/core/raft_core.rs:1416`). Three latched voters is not one degraded node: no
leader, no writes, no in-process way out — and the restart path re-derives the same failure.

**Fix.** Bypass the latch for a verified repair: in `install_snapshot`, decode and apply when
the incoming `meta.last_log_id` is strictly ahead of the failed entry, then clear the latch
only on a *verified* successful install. Add `ConsensusHealth::clear_if_verified(...)`.

**Test (red first).** Latch a machine via a failing apply, then `install_snapshot` a valid
newer snapshot → assert `Ok` **and** `is_healthy()`. Current coverage asserts the opposite
direction only (`:9516-9528`).

**Follow-on.** #40 (latch does not survive restart) and #37 (repair position not durable)
are the same wound from the other side: write the failure into the `RecoverySession` journal
(`recovery_session.rs:296-317` already has `RecoveryPhase::Quarantined` + `failed_at`) so
boot's existing `startup_reason` branch covers the snapshot path too.

### C2 — A destructive effect lands before the record that explains it `[#30]` — data loss

**Defect.** `apply_command` calls `engine.unregister_table_classified(&tid)`
(`state_machine.rs:1869-1888`) **before** the ordered `TableDropped` system write is attempted
(`flush_pending_system_writes`, `:2691-2716`). `unregister_table_classified` both records a
durable drop and deletes the SSTable directory (`engine.rs:5945-5957`, `:6098-6143`), and on
success **clears the pending-sweep flag** (`:6138`). If the system write then fails, the entry
never publishes, the staged state is discarded, and the rows are gone — with the table
re-advertised empty and every replica agreeing.

**Why this is second.** C1 is recoverable by operator action on the Raft directory. This one
destroys SSTable bytes and then removes the marker that anti-entropy would otherwise look for.

**Fix.** Invert the order inside the apply job: flush the `TableDropped` mutation first, call
`unregister_table_classified` only after `sync_projection` returns `Ok`. The job already owns
the compaction `pauses` that make this safe.

**Test.** A `SystemTableWriter` whose `apply(TableDropped)` fails → apply the `DropTable`
entry, restart over the same snapshot, assert the table is still readable with its rows
(`sstable_count(tid) > 0`). `tests/refused_ddl_latch.rs:152,302` covers the refusal boundary
but not a *failing projector*.

### C3 — The staged apply is visible before it publishes `[#43]` — wrong answers, every write group

**Defect.** `staged_apply` deep-clones `state` but only `Arc`-clones `schema`, `engine` and
`system_writer` (`state_machine.rs:626-646`). The job runs on `raft-physical-apply`
(`:2945-2985`) while `last_applied` still names the previous entry (publication at `:699`).
Nothing fences readers in that window: readiness consults no lifecycle state, and CQL reads
`schema` directly through the shared `ArcSwap` (`ferrosa-schema/src/registry.rs:317-395`).
A table is visible in `system_schema` before the engine has accepted its rows.

**Why this is third, not first.** It is transient (one job duration), so it produces wrong
answers rather than lost data — but it is on the hot path of *every* apply group, which is a
far higher hit rate than C1 or C2.

**Fix.** Publish `schema`/`engine` mutations only when `CompletedApply` is adopted, or gate
read-side `Schema` publication on the same `PhysicalApplyLifecycle` lease via an
`admit()` check.

**Test.** Start a job with a slow `apply_command` seam; read `state()`/`schema().snapshot()`
from another task; assert the new table is absent until `finish_pending_apply` returns.

### C4 — A Postgres transaction is not atomic against a crash `[#54, #50]` — wrong answers

**Defect.** Durability-before-ack holds: `engine.write_atomic_batch(source)` →
`write_atomic_batch_inner(source, None)` (`engine.rs:10231-10232`) appends, `force_sync()`
(`:10332`), then applies (`:10334-10341`), and `COMMIT` is acked afterwards. But the
single-record path is **not used**: `apply_batch` builds the CRC-protected envelope
(`engine/write.rs:265-274` → `write_atomic_batch_inner(mutations, Some(record))` →
`append_transaction_record`) and its only callers are `BatchTxn::commit` for **CQL/Bolt and
graph**. Nothing in `ferrosa-postgres` calls it. So a PG transaction's mutations are separate
log entries, and a crash after a prefix lands leaves that prefix replayable with no
transaction boundary — a transaction that was never acked becomes partially visible.

`transaction_record.rs` states the intent exactly: *"A bounded local transaction occupies one
CRC-protected WAL entry. A torn record therefore yields no mutations."* The mechanism exists;
one front end does not use it.

**Fix.** Route `commit_mutations` through `apply_batch` (or give `write_atomic_batch` an
optional envelope) so a multi-mutation set is one record. The Accord distributed path
(`accord/apply.rs:1361`) has the same shape and should follow.

**Test.** The analogue of `tests/batch_primitive.rs:579
apply_batch_torn_log_does_not_replay_prefix`, driven through `query::commit_mutations` with
`periodic_one_hour()` and three mutations: truncate mid-log, reopen, assert **zero** rows.

**Blocks:** #53 (`SERIALIZABLE isolation`) and #48 (read-set capture) both presuppose a
transaction boundary that spans the commit; without C4 the SQL transactional story has no
foundation, so do not schedule them ahead of it.

### C5 — The canonical form depends on the writer's clock `[#12]` — wrong answers, non-reproducible writes

**Defect.** `ferrosa-row-bridge/src/row.rs` stamps expiry from `SystemTime::now()` in three
places per `build_row` (`:832`, `:842-848`, `:859-865`) plus `build_delete_row` (`:889-892`).
Re-running an identical statement therefore produces different cells, and one row can carry
two different `local_deletion_time` values if the clock ticks mid-build.

This is not cosmetic: `local_deletion_time` **is** a merge tiebreaker —
`complex_cell.rs:88-97` compares `ttl` then `local_deletion_time` after `timestamp` and
`is_tombstone`. Two replicas writing the same value at the same timestamp with clocks a
second apart resolve to whichever has the larger `ldt`, and the retained cell inherits that
replica's expiry. Clock skew decides both the winner and the expiry.

**Fix.** Derive deletion time from the write timestamp, not the clock:
`timestamp.div_euclid(1_000_000) + ttl` — the shape the graph and `deletion_at` paths already
use (`engine.rs:293-298`, `expand.rs:5887`). Then the cell is a pure function of
`(value, timestamp, ttl)`.

**Test.** Build the same row twice with an advanced clock; assert `CellValue` equality, and
`merge_rows(a,b) == merge_rows(b,a)` for a same-timestamp cell whose `ldt` differs.

### C6 — A TTL past 2038 silently means "never expires" `[#72, #8]` — wrong answers, quiet

**Defect.** The field is `i32` (`ferrosa-common/src/cell.rs:52`,
`ferrosa-sstable/src/types.rs:92`). The ledger says the value *wraps negative* and the row
expires early. That is not what the code does: `row.rs:846-848` and `:863-865`
**saturate** to `i32::MAX`, which is `NO_DELETION_TIME` — the "never expires" sentinel. Then
`writer.rs:2714-2716` refuses to treat the cell as expiring at all, so the TTL flag is dropped
and the cell round-trips as `ttl = NO_TTL`. Nothing caps `USING TTL`
(`router.rs:9413-9423` only range-checks `i32`).

So the real failure is the opposite of the claim and arguably worse: a customer asks for a
12-year TTL, gets **permanent** data, and no error. (A negative TTL saturates the same way.)

**Fix.** Refuse rather than saturate: `checked_add` → reject the statement with "TTL beyond
2038-01-19 is not representable". Keep `NO_DELETION_TIME` for "no expiry" only.

**Test.** `INSERT … USING TTL` with `now+ttl > i32::MAX - 1` must be rejected. Today the row
is readable forever and the flushed cell reports `ttl()` = NULL.

**Related, low priority:** #8 — `telemetry/writer.rs:131` does a bare `(ts / 1_000_000) as i32`
where `expand.rs:5887` and `reconcile.rs:866` clamp. It writes to a table that skips the commit
log (`engine.rs:10111-10125`), so the blast radius is `system_observability.spans` only, and
only from 2038. Fold into the C6 PR as a one-line clamp plus
`reconcile.rs:1119` (also unclamped, `u32`).

### C7 — Projection ordering still rests on the wall clock `[#42, #93, #94, #96, #90, #92]` — 6 reds, wrong answers

**Defect.** No row carries a sequence, generation or log index; the only version is the cell
timestamp from `now_micros()` (`ferrosa-schema/src/system/persistence.rs:417-432`,
`system_table_writer.rs:164-181`). At an equal timestamp the winner is decided by the serialized
payload (`merge.rs:177-190`), which is `serde_json` of a `HashSet`-derived `Vec`
(`persistence.rs:421-423`) — so ordering depends on set iteration order, not on which write the
log applied later. A later revoke can lose to an earlier grant.

**Note.** #95 is *already closed*: memtable and read/compaction now share `reconcile_cmp`. What
remains is that the shared comparator's tie-break is payload-shaped rather than causal.

**Fix.** Carry a per-cell `(log_index, generation)` and order on it before the timestamp. That
is one column and one comparator change, and it closes all six in one design — which is why
they belong in a single packet rather than six.

**Test.** Two writes to one cell with an equal timestamp, applied in log order A→B: assert the
persisted row equals B regardless of payload sort, on both the memtable and SSTDable paths.

## Tier 2 — performance

The performance class splits cleanly into **one pipeline defect** (three reds, one fix) and a
set of cheap `Arc`-plumbing wins. Perf reds are ranked by *expected production benefit*, which
is roughly concurrency-multiplied memory, not count.

### P1 — The scan tail materialises a page, then encodes it, then sends it whole `[#71, #70, #67]`

Three reds, one pipeline. This is the only item in the whole survey that can OOM a coordinator
on an ordinary query shape.

| Red | Verified site | What is wrong |
|---|---|---|
| #71 | `paging.rs:256` `DEFAULT_SCAN_PAGE_SIZE = 5_000`; `ScanBound` (`paging.rs:314-345`) has **only** `row_cap()` — no byte field anywhere | The bound is in rows. 5 000 × 1 MiB rows ≈ 5 GB. An **unpaged** request (`ScanBound::Unpaged` → `row_cap() == None`, `router.rs:2508-2512`) has no bound at all. |
| #70 | `router.rs:8549-8570` — `let mut all_rows = Vec::new()` … `extend_rows_from_partition_stream(…, &mut all_rows, …)`; the helper's own doc (`router.rs:1278-1284`) says *"memory is `O(result)`"* | Peak is the page as `Vec<Vec<Option<CqlValue>>>` **plus** the encoded page. |
| #67 | `result.rs:102-124` one `BytesMut`, `:758` `body.freeze()` then one `send`; codec copies again at `frame.rs:634-645` | One buffer per response, sent whole. `max_in_flight_per_connection = 128` (`server.rs:58`) × `max_connections_per_ip = 64` multiplies it. |

The sting: **the bounded alternative already exists and this path does not use it.**
`encode_rows_with_writer` is used for virtual tables (`router.rs:9123`) and single-partition
scans (`:5905`, `:5973`); `collect_page_from_partition_stream` (`:2494`) already paces a stream
and never holds more than a page.

**One design closes all three, because they are one pipeline:**

1. `ScanBound { page_size, max_bytes }` — a byte field enforced in the three page collectors
   (`router.rs:2494`, `:2633`, `:2693`).
2. Route the general SELECT tail through `encode_rows_with_writer` instead of
   `all_rows` + `encode_rows_paged`. This changes `RouteResult::Result(BytesMut)`
   (`router.rs:3056`) and `SpawnedResponse` (`connection.rs:1170`) into a chunk/stream body.
3. A chunked writer in `frame.rs` that flushes at a byte threshold instead of
   `dst.put_slice(&item.body)` (`frame.rs:645`).

Scope: `ferrosa-cql`-internal plus a small `ferrosa-common` addition. It does not cross into
storage. **Invasive**, but it is the highest-value work in Tier 2 by a wide margin.

**Test.** A 1 MiB-row table, a `SELECT *` with no explicit page size, and a peak-RSS
assertion on the coordinator; plus a slow-client test that asserts occupancy is bounded by the
byte threshold rather than the response size. `ferrosa-cql/tests/result_streaming_memory_bound.rs`
is the natural home.

## Sequencing

```
Tier 0  T0-1 → T0-2 → T0-3 → T0-4      book is honest; count is real
        │
Tier 1  C1 → C2 → C3 → C4 → C5 → C6 → C7
        │     │                    │
        │     └── C1 and C2 in one packet (same apply-path code, both availability/data loss)
        │                          └── C6 folds #8 in as a one-line clamp
        │
Tier 2  P1 (one design, 3 reds)  ‖  P2 (Arc plumbing, 6 reds)  ‖  P3 (cheap wins)
        └── P2/P3 can run in parallel with Tier 1; P1 needs its own branch (API change)
```

**Suggested first packet:** Tier 0 (T0-1..T0-4) + C1 + C2, on one integration branch. Reason:
T0 makes the count trustworthy, C1 and C2 touch the same `state_machine.rs` apply path and
are the only two items that can take down or silently damage a whole cluster.

## Rules this plan inherits (non-negotiable)

- **TDD** — red test first, in the crate that owns the code, named after the red. No row
  closes on a test that does not fail before the fix.
- **Fail loud, never fake** — C6 is precisely the "silent fallback" failure; do not fix it by
  clamping quietly.
- **Crate docs are part of done** — every packet updates the owning crate's `README.md` +
  `specs/` (`fmea.md` gets the closed failure mode, `roadmap.md` the status).
- **Never commit to `main`**, no version bumps in PRs, Conventional Commits, PR title sets the
  bump.
- **A red closes only when**: the pinning test lands **and** the Lean item is `.met` **and**
  the row leaves `REDS` **and** the count moves in the same commit.
